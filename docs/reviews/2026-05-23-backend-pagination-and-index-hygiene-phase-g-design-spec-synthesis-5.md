## Agreed Findings

- **[Medium] #2 — `list_icps` pagination is envelope-uniformity, not resource-bounding.** True observation: pagination here is cosmetic because LLM regeneration and the full normalized list happen before slicing. Add a one-line note to §2.1 #7 (or §4.2 commit 4): "ICP pagination is an envelope-convention play (API shape uniformity across v2 endpoints), not a performance play — LLM cost and response-size are determined by the full ICP set, not by the requested page. The slice happens after materialization." This makes the design intent explicit for future readers.
- **[Medium] #4 — `offset >= total` behavior undocumented.** True. Add a one-line note to §3.2 (after the Mongo example): "When `offset >= total`, both Neo4j and Mongo return an empty `items` list while `total` reflects the true count. ## Disagreed Findings

- **[High] #1 — Neo4j items+count queries are not transactionally consistent within a single request.** Substance already documented in §6 Risk #2: "the two queries are not atomic so a concurrent write can leave `total` slightly out of step with `len(items)`." This is the same within-request inconsistency the reviewer flags. The reviewer's suggestion (a) — wrapping in `session.execute_read()` — would be a Phase G code-scope expansion the spec explicitly chose against; suggestion (b) — documenting the contract — is already covered by Risk #2 plus the `has_more` swap-in trigger in §8 #4. The "within-request" framing is sharper than "concurrent write can leave total slightly out of step" but the underlying property and mitigation are identical. No spec change — but see Severity Disagreements below.
- **[Medium] #3 — §2.3 "No removal of any service function" misleading.** Disagreed: the spec already contains the explicit exception. §2.3 reads: "Service functions gain parameters; signatures change additively, **with one exception: `get_leads_for_org` drops the now-redundant `order_by_recent` parameter (mandatory `ORDER BY` in the new Cypher makes the flag dead — see §3.2 and §4.2 commit 7)**." Bold mine — this was added in round 3 (Finding #7). The reviewer's suggestion would replace the existing exception phrasing with semantically equivalent language. No spec change.
- **[Medium] #7 — No performance target for count queries.** Disagreed per CLAUDE.md anti-overengineering guidance: "Don't add error handling, fallbacks, or validation for scenarios that can't happen. Trust internal code and framework guarantees." Adding a `pytest --durations` baseline assertion or a "p95 < 200ms on 10k rows" gate is premature optimization for a project with 0 live users, no APM, and sub-10k row datasets. The existing §8 #4 trigger ("count-query latency becomes noticeable in profiling") is honest about the lack of metrics — codifying a number that no one will measure adds noise without value. Trigger remains "revisit when pain shows up", per the existing parenthetical in §8 #4. No spec change.
- **[Low] #8 — `tuple[list[X], int]` vs `NamedTuple`.** Disagreed on substance; the reviewer themselves notes "This is a style preference, not a correctness issue." The spec explicitly chose the lightweight tuple approach ("no new dataclass" in §2.1 #3) and applies it uniformly. Switching to `NamedTuple` at the service layer would add ceremony without changing semantics. The implementor is free to use one at implementation time if a callsite reads poorly, but it's not a spec-level decision. No spec change.

## Severity Disagreements

- **#1 — High → Low.** Agreed the within-request consistency property exists and should be documented, but disagreed with "High" severity. The substance is already in §6 Risk #2; the agreed action is a small phrasing tightening, not a re-design. At MVP scale (0 live users, low concurrent-write rate, sub-10k row datasets) within-request inconsistency between `total` and `len(items)` is a paper concern — a consumer who reads `total=423, items.length=2` and tries to compute `total/items.length` for some calculation is doing something approximate by nature. Severity is Low. Optional one-line tightening of §6 Risk #2: change "concurrent write can leave `total` slightly out of step with `len(items)`" to "concurrent write between the items query and the count query can leave `total` slightly out of step with `len(items)` within a single response — Neo4j sessions are not transaction boundaries, and Mongo's `.find()` + `.count_documents()` are likewise two independent operations." Operator preference whether to fold this in or leave the existing language as-is.
