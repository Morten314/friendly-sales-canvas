## Agreed Findings

- **[High] F1 — `call_with_prompt` signature contradicts between §3.5 and §4 Phase 1 step 4.** Verified: §4 Phase 1 step 4 still says `call_with_prompt(llm, name, **inputs)` — leftover from before the round-2 F1 revision that dropped the `llm` parameter. Updating Phase 1 step 4 to `call_with_prompt(name, **inputs)` matching §3.5.
- **[High] F2 — `retry_policy` listed in §2.1 scope but removed from §3.2 schema.** Verified: §2.1's "Per-prompt YAML front-matter carrying ... retry_policy ..." was not updated when round-1 F6 removed `retry_policy` from the schema. Removing `retry_policy` from the §2.1 enumeration (no parenthetical "(v2)" — out-of-scope is already covered in §2.2 by absence; mentioning it explicitly invites confusion).
- **[High] F3 — Module-level `render()` / `get_config()` need explicit `app.state` access mechanism.** Adding to §3.3 boot lifecycle: the module maintains a module-level singleton `_registry: Registry | None = None` set by `init_registry()` before returning. `app.state.prompts` and `_registry` reference the same `Registry` object (no copy). Module-level wrappers (`render()`, `get_config()`, `list_prompts()`) read from `_registry`; raise `RuntimeError("init_registry not called")` if accessed before initialization. Tests calling `init_registry(test_root)` replace the module singleton (acceptable in test contexts; production lifespan calls it exactly once).
- **[High] F4 — Include-depth test assertion contradicts §3.4 depth-1 limit.** Verified at spec line 511: "Include depth >2 rejected at boot" is leftover from before round-1 F7 (which lowered the limit from 2 to 1). Fixing to "Include depth >1 rejected at boot (i.e. partials may not include other partials)."
- **[Medium] F5 — `_PROMPTS_ROOT` path fragility.** Adding a boot-time assertion at step 0: `assert _PROMPTS_ROOT.is_dir() and (_PROMPTS_ROOT / "_shared").is_dir(), f"Prompts root not found at {_PROMPTS_ROOT}"`. Empty registry is a likely silent failure during repo reorganizations; loud failure at boot beats subtle confusion later.
- **[Medium] F6 — LLM factory "two models" miscounts Claude.** Verified: `signals/prompts.py` defines `_SIGNAL_ASK_CLAUDE_PROMPT_TEMPLATE`, and §3.1 lists `signal_ask_claude.md.j2`. Whether Claude is a separate model registration depends on routing (direct Anthropic API vs Together's Claude variant vs reusing the Qwen client with a Claude persona). Revising §3.5 to drop the explicit "two" count and instead say "registers the models in use today as confirmed by Phase 0 audit; current known set includes `Qwen/Qwen3-235B-A22B-Instruct-2507-tput` and `llama-3.3-70b-versatile`, plus the Claude path referenced by `_SIGNAL_ASK_CLAUDE_PROMPT_TEMPLATE` if it routes to a distinct provider." The audit confirms the final registration list before Phase 1 lands.
- **[Medium] F7 + F11 paired revision — `content_hash` algorithm + `as_langchain()` include expansion use the same well-defined textual algorithm.** Reviewer's F7 raised four sub-questions; F11 raised the LangChain-drift risk. Resolving both by specifying one textual-substitution algorithm and reusing it. Specifically:
  - **Source-expansion algorithm (used by both content_hash and `as_langchain`):** Read the prompt's `.md.j2` file body (front-matter stripped). For each `{% include 'PATH' %}` directive (matched by literal token; Jinja2 disallows `{% %}` inside string literals so a textual scan is safe): read PATH's file, strip its front-matter, and textually substitute the partial body in place of the entire `{% include %}` line (preserving the line's leading whitespace contribution to the parent body but consuming the line's trailing newline). Expansion is unconditional — `{% include %}` inside `{% if %}` is expanded regardless of the conditional. Recursive, bounded by the include-depth limit (currently 1, so depth-2 partial-includes-partial is rejected at boot, making the recursion trivial in v1).
  - **`content_hash` uses this expansion + SHA-256.** Updates §3.3 step 7 to reference the algorithm precisely.
  - **`as_langchain(name)` calls this expansion to produce a self-contained Jinja2 template body, then hands it to `PromptTemplate.from_template(body, template_format='jinja2')`.** Updates §3.4 LangChain interop Caveat 1: includes ARE allowed in LangChain-consumed prompts, and `as_langchain()` resolves them before construction. The drift risk F11 raised is eliminated — shared partial edits propagate to LangChain prompts automatically.
- **[Medium] F8 — No encoding or parse-error resilience specified.** Adding to §3.3 boot step 2: "Per-file parse errors (UTF-8 decode failures, malformed YAML, missing closing `---` fence, BOM-only files) are captured as `FailureDetail` entries and aggregated into `BootFailure`; processing continues for remaining files. BOMs at file head are stripped silently (UTF-8 BOM is allowed but not required)."
- **[Medium] F9 — No validation that `_shared/defaults.yaml` exists.** Adding step 0 to the boot lifecycle (before the file walk): "Load and parse `_shared/defaults.yaml`. If missing, raise `BootFailure([FailureDetail(file='_shared/defaults.yaml', error='missing required file')])` immediately. If present but malformed YAML, raise `BootFailure` with the YAML error captured."
- **[Medium] F10 — No performance/latency budget.** Adding a non-functional note at the end of §3.3 boot lifecycle: "Expected boot-time initialization: <1 second for up to 200 prompt files on Render's standard runtime. If the prompt corpus grows past this ceiling, the loader can be extended with lazy per-prompt loading or a pre-compiled cache without changing the public API."
- **[Low] F12 — `signals/prompts.py` LOC drift (328 → 325).** Verified via `wc -l` cited by reviewer. Fixing §7 reference.
- **[Low] F13 — `render()` async-safety not stated.** Adding to `render()`'s public-surface docstring in §3.3: "Pure computation (no I/O); safe to call from async handlers without blocking the event loop."
- **[Low] F15 — Phase 2 rollback guidance.** Adding to §4 Phase 2 per-service commit list: "Rollback path = PR revert; no shim layer (per CLAUDE.md no-backwards-compat-shims rule). A reverted PR removes the prompt files, the call-site changes, and the persistence/fixture changes atomically."
- **[Low] F16 — `prompt_meta` not indexed.** Adding to §3.5 "Coverage during migration": "No Mongo index on `prompt_meta.*` fields in v1. For pre-launch data volumes this is fine; analytics queries scan the collection. Add a compound index on `{org_id: 1, 'prompt_meta.name': 1, 'prompt_meta.version': 1}` when analytics query latency or volume justifies it."
- **[Nit] F17 — `market_scoring/` cited as Phase-0-discovered example but already in baseline.** Verified: §2.1 already lists `market_scoring/orchestrator.py:282-325`. Replacing the §3.1 example with `customer_profile/` (a service that's not in the baseline inventory but may have inline prompts surfaced by the audit).
- **[Nit] F18 — Golden fixture branch coverage ambiguity.** Adding to §3.6 Layer 2 sizing guidance: "Golden fixtures exercise one canonical path per prompt — the happy path with all conditional sections active. Fallback/empty-branch rendering is covered by Layer 1 unit tests against synthetic `tmp_path` prompts, not by golden fixtures. This keeps the fixture corpus small and the assertion focused on 'what changed in the prompt' rather than 'is every branch reachable.'"
- **[Nit] F19 — Jinja2 expression delimiter note.** Adding a one-sentence clarification to §3.4 JSON-example handling: "Authors who need a literal `{{` in prompt output should use `{{ '{{' }}` (Jinja2's standard escape). The triple-brace edge case (`{{{`) parses correctly as `{{` (expression start) followed by `{` (literal) — but is unlikely in practice."

## Open Questions

- **F6 follow-on — Claude routing.** The Phase 0 audit must confirm whether `_SIGNAL_ASK_CLAUDE_PROMPT_TEMPLATE`'s `signal_ask_claude` function routes to (a) a direct Anthropic API call (new client to register), (b) Together's Claude-compatible endpoint via the existing `llm2` client (no new registration), or (c) the same Qwen client (just stylistically "Claude-ish"). The factory registration list cannot be finalized until the audit answers this. The spec acknowledges this; the audit produces the authoritative model list.
- **F7/F11 follow-on — partial expansion preserving Jinja2 control structures.** The agreed source-expansion algorithm replaces `{% include %}` directives unconditionally. But the partial's body may itself contain Jinja2 control structures (`{% if %}`, `{{ var }}`). For `content_hash`, this is fine (the hash is over source text). For `as_langchain()`, the partial's `{% if %}` and `{{ var }}` are passed to LangChain's Jinja2 environment for evaluation at chain time. Edge case: if a partial uses a variable that the includer's front-matter doesn't declare but the partial's docstring does (only relevant for partials with their own variable usage), the AST walk at boot catches this (declared inputs must cover transitive references). Flagging the interaction for the implementation pass: the include-expansion's textual nature must preserve Jinja2 syntax in the partial's body so LangChain can evaluate it.
- **F11 follow-on — LangChain Jinja2 environment limitations on expanded body.** With includes expanded, LangChain's Jinja2 still renders the resulting template — and LangChain's environment doesn't use `StrictUndefined` (Caveat 2 from round 2). The boot-time AST walk on the expanded body must validate that every variable referenced is declared in `inputs:`. The plan should verify this validation pass operates on the expanded body, not the un-expanded source, for LangChain-consumed prompts.
