## Findings

### [Low] Lock-message feedback is not announced to assistive tech, defeating the "explain itself" rationale of the styled-disabled CTA

**Location:** `frontend/src/features/signals/components/SignalCard.tsx:334-337` (the lock `<p>`); CTA button at `SignalCard.tsx:322-326`.

The locked `[Find Matched Leads]` button is *functionally* enabled (not native-disabled) specifically so clicking it explains the lock — spec §2's stated purpose is that the control "can explain itself." The button exposes `aria-disabled={!isAccepted}` (`:324`), so a screen reader announces it as "disabled." But the explanatory message that appears on click (`<p>…Accept this signal to unlock matched leads…</p>`, `:335-336`) has no `role="status"` / `aria-live`, so it is **not** announced. The net effect for AT users: a "disabled" button that, when activated, silently does nothing perceivable — the exact opposite of the design intent.

Fix: add `role="status"` (or `aria-live="polite"`) to the lock-message `<p>`. Low because the repo ships no `jsx-a11y` gate and is pre-launch/0-users, but it is a genuine gap in the feature's stated purpose. (Minor related Nit: `role="button"` at `:323` is redundant on a native `<button>` — harmless and lint-inert without `jsx-a11y`, but it can be dropped per the ARIA "no redundant roles" guidance.)

### [Low] PDF footer literal `•` is not routed through `escapePdfText` and mojibakes — the one content-stream string the in-scope fold missed

**Location:** `frontend/src/features/artifacts/lib/artefactPdf.ts:101` (`(Generated by Brewra AI • ${date}) Tj`); the bullet fold at `artefactPdf.ts:14`.

`createSimplePDF` routes every free-text field through `escapePdfText`, which folds `•` → `-` precisely because bullets mojibake under the generator's Helvetica/WinAnsi font (spec §5). The footer line carries a literal `•` (`U+2022`, UTF-8 `E2 80 A2`) directly into the `Tj` stream; under WinAnsi that renders as `â€¢`, so every briefing footer reads *"Generated by Brewra AI â€¢ 6/19/2026."* It is the only non-ASCII *constant* in the content stream — every other literal (`EXECUTIVE SUMMARY`, `Task ID:`, etc.) is ASCII. This is **not** covered by the deferred TD-FE-78 "residual non-ASCII beyond the common fold" caveat, because `•` is explicitly *in* the fold set the branch added, so it is a missed application of the in-scope escaping, not a deferred generator issue. (Pre-existing on `master:85`; surfaced here because the branch hardened exactly this defect class everywhere else.) Fix: route the footer through `escapePdfText`, or replace the literal `•` with `-`.

### [Nit] The multi-item drain ordering in `ArtifactsPage` (reverse + mostRecent) has no test coverage

**Location:** `frontend/src/features/artifacts/pages/ArtifactsPage.tsx:67-71` (`setArtefacts((prev) => [...queued.slice().reverse(), ...prev])` and `mostRecent = queued[queued.length - 1]`); tests at `ArtifactsPage.test.tsx`.

The drain logic is designed for ≥2 queued briefings (reverse so the most-recently-enqueued lands first, mirroring per-event prepend; `mostRecent` = last enqueued). But `ArtifactsPage.test.tsx` only ever enqueues a **single** item. A regression in the multi-item path (e.g. dropping `.reverse()`, or indexing `queued[0]` instead of the last) would pass the suite. Add a two-item case asserting final order and which item gets its folder opened/expanded.
